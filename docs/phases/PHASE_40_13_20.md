# Phase 40.13.20 — Production autoscaling qualification

Phase 40.13.20 implements and qualifies the Kubernetes control chain that preserves twenty percent
CPU and memory headroom across every independently scalable c8 responsibility.

## Control chain

1. Rust services derive their CPU and finite memory envelope from cgroup v2.
2. HPA owns online query, fragment, hydration, and online-reasoner replica demand.
3. Operators own ingestion, compilation, indexing, offline reasoning, and recovery Indexed Jobs.
4. In the production qualification overlay KEDA owns hydration while HPA owns query, fragment, and
   online reasoning; HPA and KEDA cannot own the
   same target.
5. Kueue admits batch CPU and memory by responsibility flavor.
6. Pods select exactly one `ngkg.io/workload` node pool and use Guaranteed-QoS requests equal to
   limits.
7. At CPU **or** memory utilization of 80 percent, or when admitted work remains pending, the pod
   owner creates additional demand.
8. The externally managed provider adapter expands the matching RKE/RKE2, EKS, AKS, GKE, or
   generic Kubernetes node pool when that demand is unschedulable.
9. Batch pools may scale from zero; query-facing pools retain their qualified availability floor.
10. Scale-down is allowed only after active work, checkpoint, spill, and response-spool gauges reach
    zero and disruption budgets permit drain.

Cluster Autoscaler does not consume live node utilization directly. The production invariant is
implemented by 80-percent HPA/custom-metric targets, accurate requests, one-pod-per-node
anti-affinity where required, and pending responsibility-specific pods. The node provisioner reacts
to the resulting unschedulable demand. This avoids a second controller racing the scheduler or
directly changing provider node-pool size.

## Portable provider profiles

Apply the common production overlay and exactly one provider overlay:

| Kubernetes target | Provider overlay | Node provisioner |
|---|---|---|
| Generic conformant Kubernetes | `phase40.13.20-generic.yaml` | external Cluster Autoscaler |
| RKE | `phase40.13.20-rke.yaml` | Rancher Cluster Autoscaler |
| RKE2 | `phase40.13.20-rke2.yaml` | Rancher Cluster Autoscaler |
| Amazon EKS | `phase40.13.20-eks.yaml` | Karpenter |
| Microsoft AKS | `phase40.13.20-aks.yaml` | managed Cluster Autoscaler |
| Google GKE | `phase40.13.20-gke.yaml` | managed Cluster Autoscaler |

The chart owns neither cloud credentials nor the provider autoscaler. It records the external
discovery resource, validates that it matches the selected distribution, and creates only NGKG
pod-level demand. Provider-managed workload identity supplies cloud access.

## Portable TriG bucket mounts

Existing TriG acquisition remains a read-only CSI path for all three object stores:

| Source provider | Qualified CSI driver | Identity path |
|---|---|---|
| Amazon S3 | `s3.csi.aws.com` | pod/service-account workload identity |
| Azure Blob Storage | `blob.csi.azure.com` | Azure Workload Identity client ID |
| Google Cloud Storage | `gcsfuse.csi.storage.gke.io` | GKE Workload Identity plus GCS FUSE injection |

Before creating a PV, the operator now verifies that the selected `CSIDriver` is registered. PV,
PVC, and container mount remain `ReadOnlyMany`/read-only. The worker never lists an artifact store;
it freezes only explicit keys or the authorized prefix into the existing checksum-bound cloud
source manifest, and whole-TriG compilation consumes that immutable handoff.

## Executable policy

`ngkg-autoscaling` validates every pool policy, charges the larger of requested and observed CPU or
memory, and returns deterministic `scale-out`, `scale-from-zero`, `hold`, `scale-in`, or
`scale-in-blocked` evidence. Exactly 80 percent triggers scale-out. Requested resources are included
so delayed metrics cannot hide scheduler pressure.

The same crate rejects qualification unless every reviewed workload is covered and baseline versus
scaled/node-loss/retry result hashes and artifact-root hashes are identical. Kueue admission, node
provisioning, scale-from-zero, and node-loss must all be live observations.

## Cgroup budgets

`ngkg-hpc-runtime` reads `cpuset.cpus.effective`, `memory.max`, and `memory.current`. Unlimited memory
cgroups fail closed. Storage recovery uses the remaining memory inside the 80-percent envelope to
admit multipart buffers before any object transfer. This complements its existing task-byte,
scratch, multipart-concurrency, and all-partitions certificate limits.

## Production overlay

Install the workload chart with both the normal production custom-metric overlay and:

```bash
helm upgrade --install ngkg-workloads charts/ngkg-workloads \
  --namespace ngkg \
  --values approved-values.yaml \
  --values charts/ngkg-workloads/profiles/production-workload-autoscaling.yaml \
  --values charts/ngkg-workloads/profiles/phase40.13.20-production.yaml \
  --values charts/ngkg-workloads/profiles/phase40.13.20-eks.yaml
```

Replace the last overlay with the target platform. RKE/RKE2 deployments reference an approved
Rancher cloud-config Secret; EKS, AKS, and GKE use their reviewed workload-identity and managed
node-pool configuration. The chart creates none of those credentials.

## Live qualification

After an approved load and chaos run has produced an event log and determinism matrix:

```bash
python3 qualification/run_phase40_13_20_live.py \
  --event-log qualification/live/phase40.13.20-events.json \
  --determinism qualification/live/phase40.13.20-determinism.json \
  --provider eks \
  --source-provider aws-s3 \
  --output qualification/live/phase40.13.20-report.json
```

The harness reads HPA, Metrics Server, custom metrics, Kueue, KEDA, node labels, selected provider
state, and registered CSI drivers. It performs no mutation. Missing APIs, an unavailable selected
CSI driver, missing responsibility pools, a target other than 80, missing scale or node-loss
events, or any checksum difference produces a nonzero exit and an incomplete report.

## Prerequisite boundary

Production qualification also requires native Rust compilation/tests, rendered Helm validation,
PostgreSQL and object-store integration, a real multinode target cluster, configured provider node
pools and source CSI driver, Kueue, metrics adapters, and approved fault injection. Absence of any
prerequisite blocks the qualification certificate. Static source checks are not a substitute.

No ontology alignment, schema matching, or raw-data mapping is implemented by this phase.
