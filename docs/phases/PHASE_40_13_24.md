# Phase 40.13.24 — Kubernetes release qualification

Phase 40.13.24 turns the source-implemented semantic database into a release-gated Kubernetes candidate. It does not declare the source tree production-qualified. It defines and enforces the evidence that must be generated on isolated high-availability RKE, RKE2, EKS, AKS, and GKE clusters before a certificate can exist.

## Semantic release prerequisite

The release gate includes a content-bound `CONSTRUCT` corpus spanning security, infrastructure, organization, and enterprise ontology graphs. An OWL 2 DL property-chain consequence joins three asserted hops across four authorized `https://c8-next-generation.io/<scope>/<subdomain>/semkg` graphs. The public result is one canonical RDF context graph containing asserted context plus the inferred response relationship.

Admission requires an OWL 2 DL profile/consistency identity, the exact snapshot and authorized-graph identities, complete proof/support coverage, at least two activated Kubernetes nodes, multiple cores, at least one reasoned output triple, and byte-independent canonical graph equality with the scalar Rust oracle. The ordinary fast path reads certified finite closure and semantic indexes produced by distributed workers. Uncovered legal Direct-Semantics BGP candidates use the bounded exact-reasoner partitions and exhaustive completion barrier. HermiT remains a pinned correctness boundary; it is not represented as an arbitrarily decomposable distributed reasoner. Apache Jena is not part of this path or any NGKG production image.

## HPC and multi-node execution

Non-disruptive cases execute as Kueue-admitted Kubernetes Indexed Jobs. Stable hashing assigns cases to dense partitions, each pod receives whole cores and fixed RAM, Rust uses multiple bounded worker threads inside each pod, and topology spread plus required anti-affinity distributes pods across worker nodes and zones. OpenMP and BLAS thread counts stay at one so native libraries cannot multiply the Rust/Kubernetes concurrency budget. Every partition writes one immutable report and the reducer refuses missing indexes, duplicates, reused worker identities, incomplete observations, resource undershoot, or result drift.

Disruptive cases are intentionally separate and serialized. The driver will not invoke a node, network, storage, upgrade, rollback, or restore disruption unless the scenario targets an isolated qualification cluster and the caller supplies explicit approval evidence whose SHA-256 is bound into the plan. This prevents a source verification or Helm render from accidentally running chaos against a production cluster.

## Required release evidence

All five Kubernetes targets must cover the closed gate set: 72-hour multinode soak; pod/node, network, and storage chaos; upgrade and rollback; backup/restore with measured RPO/RTO; Helm lint/render/install/upgrade; digest-pinned non-root images; signature and provenance verification; SPDX and CycloneDX SBOMs; zero unwaived critical/high CVEs; closed license policy; two isolated reproducible builders; and AWS/Azure/GCP/RKE object-storage ingestion portability. Concurrent ingestion, compilation, reasoning, property paths, SPARQL, recovery, and 80%-CPU-or-memory autoscaling must retain identical semantic output.

The final certificate binds the Phase 40.13.23 performance certificate, semantic prerequisite evidence, release identity, inventory, plans, every raw observation, and a deterministic evidence root. Synthetic execution proves only that the harness and rejection paths work. A production certificate requires real release images, enterprise datasets, cloud clusters, multi-node soak time, injected failures, supply-chain tooling, and retained evidence.

After this phase, two milestones remain: Phase 1.0.0-RC1 freezes and signs the release candidate; Phase 1.0.0 resolves acceptance defects and publishes General Availability artifacts.
