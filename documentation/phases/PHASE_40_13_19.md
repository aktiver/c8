# Phase 40.13.19 — multinode storage and recovery

## Runtime design

Published RDF/OWL snapshots remain immutable. The control API derives a complete storage manifest
from the catalog-bound snapshot manifest, registers an idempotent operation in PostgreSQL, writes a
checksum-bound recovery plan, and creates an `NgkgStorageRecovery` resource. No operation changes
RDF terms, named graphs, ontology axioms, closure semantics, or query answers.

Replica placement uses deterministic rendezvous hashing across distinct operator-declared failure
domains. Relocation copies and verifies the replacement before the catalog marks an old replica
`RETIRING`. Compute-node loss repeats the same Kubernetes completion index and stable BLAKE3 work
identity. An immutable destination conflict or checksum mismatch is a quarantine failure, never a
cache miss or an empty partition.

## HPC and Kubernetes execution

Each artifact copy is one logical Indexed Job completion. The plan's task count is independent of
current pod count; `maxParallelism`, Kueue quota, whole-core requests, and the dedicated
`ngkg.io/workload=storage-recovery` node pool bound concurrent work and create Cluster Autoscaler
demand. Object streams use bounded ephemeral scratch and multipart buffers. Rust/pod concurrency
uses cores and nodes while OpenMP, OpenBLAS, and MKL remain at one thread because copying and SHA-256
are streaming/sparse kernels, not dense matrix workloads.

The API reduces requested parallelism so `largestTaskBytes × maxParallelism` never exceeds the
operation's aggregate byte budget, and the operator rechecks that bound before creating work. The
default worker supports artifacts up to 60 GiB in a 64 GiB ephemeral-storage envelope; the earlier
cloud compiler partitions very large TriG inputs into independently recoverable artifacts. The
recovery pool has a zero-to-32-node envelope, while two disruption-budgeted operator replicas stay
resident.

The finalizer streams every exact result key through a constant-additional-memory accumulator and
issues a recovery certificate only when indexes are dense, unique, successful, byte-exact, and
checksum-exact. A missing result, duplicate index,
timeout, target failure, or corrupt replica fails the barrier. Controller replicas remain running
and protected by a disruption budget; worker capacity may scale from zero through queued Jobs.

## Backup and restore

A backup manifest maps every original object key to a verified immutable backup key and binds the
snapshot, storage manifest, certificate, byte total, and target. Restore resolves the cataloged
backup ID, copies every object into a new inactive namespace, and emits a `storage-verified`
certificate. Catalog import and publication remain separate atomic actions so partial restore bytes
cannot become queryable.

## Explicit boundary

This is storage placement and disaster recovery, not ontology alignment and not raw-data mapping.
Only artifacts already belonging to a certified snapshot are copied. Live node/zone failure,
cross-region object stores, backup retention, and catalog-import publication still require the
Phase 40.13.19 live qualification environment before production claims are enabled.
