# Phase 40.13.17 — partition-native distributed property paths

## Runtime boundary

This phase connects typed SPARQL property-path plans to the immutable adjacency partitions emitted
by Phase 40.13.12. It does not ingest raw data, align ontologies, match schemas, or add inferred
axioms. Authorization and active-dataset selection occur before any semantic artifact is loaded.

Each frontier iteration fans out to every semantic storage partition. A worker checksum-validates
its semantic root, partition manifest, dictionary, and forward/reverse adjacency files, then
binary-seeks only admitted frontier vertices. Default paths use only active default graphs;
`GRAPH <iri>` stays inside one authorized named graph; `GRAPH ?g` carries graph identity in every
state and endpoint.

## HPC execution

- Semantic partitions are assigned deterministically across distinct fragment-worker pod IPs.
- A high-degree vertex is split into stable edge shards and evaluated over a bounded native Rust
  thread pool without cloning its adjacency vector per shard.
- Fixed-subject leaves binary-seek both forward and reverse indexes. Variable-subject leaves scan
  each immutable partition once under a row ceiling.
- Frontiers, visited states, and endpoint pairs are ordered sets, preserving SPARQL endpoint-set
  rather than route-count semantics.
- Literal objects remain valid consuming-step endpoints; they cannot become a subsequent subject.

The worker thread count must fit both the fragment exchange concurrency and the pod's cgroup-aware
Rust compute budget. OpenMP, OpenBLAS, and MKL remain single-threaded inside this Rust parallel
region, preventing nested oversubscription.

## Completion, spill, and recovery

The coordinator advances only after it receives exactly one valid response for every semantic
partition and every deterministic hot split. Missing, duplicate, foreign, corrupt, timed-out, or
partial work fails the query; it is never interpreted as an empty match. Global termination is
declared only when the merged next frontier is empty after that dense barrier.

Every completed iteration creates a bounded canonical checkpoint containing visited state,
frontier, endpoint set, and traversal identity. It is written by atomic rename to the query pod's
spill volume and then uploaded immutably under the tenant/dataset/snapshot/query/path identity.
Per-query checkpoint bytes cannot exceed the property-path spill ceiling, which itself must fit the
shared NVMe shuffle budget.

## Kubernetes scaling

Fragment-worker HPA inputs include pending path partitions and active frontier states in addition
to CPU and memory. Query-shard HPA inputs include live checkpoint bytes. These are workload signals,
not correctness inputs: pod or node count changes cannot alter partition ownership, work identity,
checkpoint checksums, or the global completion barrier.

## Activation status

The partition-native traversal runs for ordinary deterministic `/sparql` and `/query` property-path
requests on cloud-activated multipart snapshots. The Phase 40.13.16 scalar oracle still owns the
published SPARQL result while the new endpoint hashes and traversal evidence are qualified. This
preserves standards-correct answers, but removing the full scalar compatibility image for all outer
algebra contexts remains a release gate.

Native Rust, Helm render/lint, live multinode HPA/node-autoscaler behavior, restart-from-checkpoint,
and scalar differential equality must pass in the designated builder and Kubernetes environment
before the path lane can be called production-qualified.
