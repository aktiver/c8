# Phase 40.13.21 — Enterprise security and operations

Phase 40.13.21 adds the durable enterprise query-audit boundary to the autoscaling semantic read
plane and assembles the inherited workload-identity, tenant-isolation, encryption, network-policy,
admission-control, telemetry, recovery, and provider-neutral Kubernetes controls into one
operational qualification boundary.

## Query execution ledger

Every admitted JSON or SPARQL Protocol query creates a `RUNNING` PostgreSQL record before parsing or
distributed execution. The record is tenant-scoped by forced row-level security and contains the
requesting principal, request ID, query SHA-256, optional exact SPARQL text, dataset, and Unix start
time. Completion performs one guarded transition to `COMPLETED`, `FAILED`, or `TIMED_OUT`; identity
and query fields cannot change, terminal rows cannot be updated, and rows cannot be deleted.

`GET /v1/query_logs` returns a bounded, newest-first page. `GET
/v1/query_logs/{queryExecutionId}` returns one execution. A `queries:execute` principal sees only
its own records. `query-logs:read` grants tenant-wide audit visibility but does not reveal exact
query text; `query-logs:read:text` grants that separate capability. Cross-tenant lookup is
impossible through PostgreSQL RLS, and unauthorized same-tenant lookup returns the same not-found
response as a missing identity.

Each successful query response carries `x-ngkg-query-execution-id`, including SPARQL Protocol
responses, so clients can correlate their request with the ledger.

## Timing and resource evidence

The API exposes Unix epoch seconds and milliseconds, exact elapsed milliseconds, and a stable human
duration such as `1min 30s` or `230min 12s`. Minutes are intentionally unbounded.

Resource fields report the Kubernetes requested resource envelope activated by the execution:

- the query coordinator;
- the maximum distinct fragment, shuffle, or property-path worker set observed in result evidence;
- one hydration worker when payload hydration ran.

`nodesActivated` is an execution-slot count under the chart's one-worker-per-node anti-affinity
contract. `cpuMillicores`, `coresActivated`, `ramBytes`, and `ramGiB` are calculated from the
configured pod requests. They are deterministic capacity charged to the query, not sampled peak
utilization and not a claim that cross-component pods could never share a physical host in a
nonconforming custom deployment. Cache hits charge only the coordinator.

## Security behavior

Exact query text never appears in metrics or process logs. Operators may disable its durable storage
with `onlineServing.queryLogs.storeQueryText`; the SHA-256, user, resource, and timing evidence remain.
The database and backup encryption requirements from the platform deployment remain prerequisites
because this phase does not pretend plaintext application fields are independently encrypted.

Query-log reads pass through the same bounded admission controller as query traffic. Audit-only
tokens require no graph authorization labels, while query-execution tokens still require them. The
shared strict token contract accepts the two new audit scopes in both API processes so a common
checksum-bound Secret remains deployable.

## Qualification boundary

Static qualification verifies the migration, RLS, immutable transition, scopes, route/OpenAPI
parity, duration vectors, and Helm resource-envelope wiring. Production qualification still
requires PostgreSQL migration/integration tests, native Rust tests, rendered Helm validation,
provider workload identity, TLS/mTLS, encrypted database/storage/backup configuration, default-deny
policy enforcement, cross-tenant attacks, secret scanning, audit export, rate-limit exercises,
alerts/SLOs, key rotation, backup/restore, disaster recovery, and live HA testing on every claimed
RKE/RKE2, EKS, AKS, and GKE profile.

No ontology alignment, schema matching, or raw-data mapping is implemented.
