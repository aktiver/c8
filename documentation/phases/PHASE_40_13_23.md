# Phase 40.13.23 — Performance and capacity qualification

Phase 40.13.23 converts performance, scalability, and cost claims into release-bound evidence. It measures whole-TriG ingestion, distributed semantic compilation, offline reasoning, property-path traversal, ordinary SPARQL, sustained concurrent SPARQL, and recovery. The qualification matrix requires at least three content-addressed representative enterprise datasets, each at least 100 GiB with 100 million triples, 30 named graphs, OWL 2 DL qualification, pinned imports, provenance, and property-path scale where applicable. A synthetic-only run can test the harness but can never qualify a release.

## Rust production boundary

NGKG remains a complete Rust database/query implementation. The production Cargo workspace, services, operators, storage paths, Helm values, and NGKG containers do not link or embed Apache Jena. The system under measurement is the digest-pinned NGKG Rust release image.

Apache Jena is only an external competitor process for applicable SPARQL and property-path comparisons. It receives the same immutable dataset and snapshot meaning, cache state, concurrency, hardware class, and CPU/RAM ceiling through a bounded client. Its image digest is evidence in the plan, but no Jena code is copied into an NGKG runtime image or used to answer production requests. Removing the external comparison would not change NGKG behavior; it would only remove the independent performance baseline required by this phase.

HermiT remains a separately pinned OWL 2 DL correctness authority inherited from semantic qualification. Performance measurements never substitute Jena or HermiT answers for Rust answers. A trial counts only when NGKG's canonical result SHA-256 equals the expected result and, when an artifact is produced, its artifact-root identity remains deterministic.

## Reproducible evidence

The plan binds the benchmark inventory, NGKG release image, optional external Jena image, observed hardware/NUMA profile, dated USD pricing profile, Phase 40.13.20 autoscaling evidence, dataset/snapshot identities, operation descriptor, cache state, concurrency, and exact resource envelope. Hardware evidence records provider, region, node type, architecture, CPU model, physical cores, NUMA nodes, RAM, network, storage, kernel, cgroup v2, and container runtime. Pricing evidence records node, object-operation, storage, and egress inputs without embedding a volatile cloud price into source code.

Each family is tested at increasing 1-, 2-, and 4-node minimum scale points. Client concurrency includes 1, 8, 32, 100, and 250. The driver records monotonic duration, completed operations, family-specific work items, CPU time, peak RSS, read/write traffic, activated nodes/cores/RAM, result and artifact hashes, autoscaling evidence, and micro-USD cost. Throughput units are explicit: bytes for ingestion/recovery, triples for compilation, axioms for reasoning, scanned edges for property paths, and completed queries for SPARQL.

The checked NGKG driver is itself Rust. It makes bounded HTTPS requests with redirects disabled, accepts credentials only through named environment variables, applies explicit cache-control readiness, requires canonical result identities from certified responses, rejects unequal concurrent results, reads cgroup CPU/memory counters, and follows `x-ngkg-query-execution-id` to the tenant-authorized `/v1/query_logs/{id}` route for activated node/core/RAM evidence. Pricing is supplied as a dated content-bound input; node, object-operation, and egress costs are calculated from raw trial counters rather than manually entered result totals.

Warm-up indices are declared before execution and retained. At least ten measured trials per engine are mandatory. Every measured trial enters nearest-rank p50, p95, and p99 statistics. Failed, timed-out, slow, partial, corrupt, or node-loss trials cannot be deleted as outliers. Driver order alternates deterministically to reduce temporal bias, and unrelated scenarios execute sequentially so one benchmark does not contaminate another; intentional concurrency occurs inside the measured scenario.

## Claim gates

The checked policy requires exact semantic equality, scale-invariant result identity, a complete 80%-CPU-or-memory autoscaling and node-loss evidence chain, 100 GiB ingestion within 600 seconds, at least two million property-path edges per second, sustained 250-user load, normalized cost evidence, at least 20× geometric-mean speedup for applicable selective comparisons, and at least 50× median speedup for hot applicable queries. A threshold failure, missing family, missing partition, duplicate worker, omitted trial, over-envelope resource sample, or mismatched hash prevents certificate creation. These targets are qualification requirements, not claims made by the source tree.

Kubernetes uses a Kueue-admitted Indexed Job with a dense partition barrier, fixed Guaranteed-QoS resources, fixed benchmark hardware label, `parallelism: 1`, zero failed indexes, and durable raw reports. RKE/RKE2, EKS, AKS, and GKE use the provider-neutral autoscaling controls implemented in Phase 40.13.20; the benchmark binds the live scaling report rather than inferring node growth from a manifest.

This source candidate includes an executable synthetic barrier test to prove that plan construction, strict driver validation, metrics, thresholds, report merging, and corrupted-evidence rejection work. It does not contain real enterprise datasets, cloud pricing, release images, or live cluster results and therefore makes no production performance claim.
